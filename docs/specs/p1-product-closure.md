# SampleFlow P1 产品闭环与上线准备规格

> 状态：当前 P1 权威产品规格；实现状态以 `handoff.md` 和 GitHub 实时 Issue/PR 为准。
>
> 最终范围：GitHub Issues #10—#15，以及审查加固 #94—#100。当前产品只提供桌面 Web，不提供移动端；真实业务验收和公司服务器验收仍是后续 Gate，完成前不得关闭对应 Issue。常规工程实现、测试、提交、PR、CI 后合并和对应 Issue 关闭已获授权；真实发布、密钥与权限、生产数据及不可逆操作仍是人工门禁。

## Problem Statement

SampleFlow 已具备 P0 的权限、组织、不可变业绩事件、目标审批、受控 Excel 导入和隔离工程门禁，但桌面 Web 仍不足以支持完整的日常产品使用：各角色看不到统一且可穿透的正式目标达成结果，订单台账无法稳定浏览全部数据或按条件导出，省份与客户单位分析缺失，账号、组织、审批和审计操作分散，页面缺少正式路由与一致反馈，生产安全、备份恢复、可观测性和部署验收也没有闭环。

用户需要一套可在桌面浏览器完成核心工作的产品界面，并要求所有汇总继续服从既有权限、目标生效门禁、不可变事件、事件发生时组织归属和审计规则。当前产品没有移动端，桌面 Web 是唯一客户端；当前没有可用公司服务器，因此先完成仓库工程与隔离验收，公司服务器实际验收后续完成，相关 Issue 在证据齐全前保持打开。

## Solution

交付按角色授权的桌面 Web 产品闭环：统一目标达成看板、可穿透正式报表、稳定分页的订单台账、与列表同条件的导出、省份与客户单位分析、可操作的账号／组织／审批后台、按权限查询的不可修改审计，以及清晰可恢复的页面路由和无障碍交互。

地区与客户单位分析按每笔业绩事件发生时的业绩分析维度快照计算；缺少受控来源证据的历史事件不得按订单当前资料倒推，而是进入明确的“待补齐”口径。目标责任人继续实名确认具体目标版本，但不采集手写签名图片。

生产准备在仓库内完成最小权限数据库角色、非 root 容器、安全响应头、健康检查、结构化日志、核心指标、备份恢复工具、隔离 Compose 演练和运维手册。公司服务器、域名、HTTPS、备份存储、告警平台、RPO/RTO、真实迁移、业务 UAT 和生产窗口待环境就绪并取得单独授权后验收。

## User Stories

1. 作为业务员，我希望首页默认显示当前业务月的个人生效目标、个人业绩、差距和达成率，以便判断本月进展。
2. 作为业务员，我希望目标未生效时仍能查看授权范围内的订单和实际业绩，同时看到不能形成正式达成率的原因。
3. 作为业务员，我希望点击已完成业绩后查看构成该金额的正向和负向不可变事件，以便自行核对。
4. 作为业务员，我希望点击差距或负向调整后查看相关订单和事件，以便定位未达成原因。
5. 作为业务员，我希望切换年份和月份查看历史趋势，而不是只能看到硬编码月份。
6. 作为业务员，我希望系统按 `Asia/Shanghai` 的自然日显示时间进度和简单落后提示，以便获得参考而不依赖节假日配置。
7. 作为业务员，我希望活动目标金额为零时看到明确说明而不是除零后的错误达成率。
8. 作为业务员组长，我希望分别查看个人业绩与小组业绩，避免把下属业绩算成自己的个人业绩。
9. 作为业务员组长，我希望查看小组生效目标、业绩、差距、达成率和组员构成，以便管理团队。
10. 作为业务主管，我希望分别查看个人业绩与部门业绩，并穿透到小组、人员、订单和事件。
11. 作为销售经理，我希望查看授权销售范围的总目标、实际业绩、差距、达成率及各部门构成。
12. 作为人事部或总经理，我希望查看全公司各层级目标的准备状态和实际业绩，但未生效目标不能被标记为正式绩效结果。
13. 作为有导出权限的用户，我希望正式报表导出和页面采用同一目标生效门禁、权限范围和金额口径。
14. 作为审计人员，我希望任一看板汇总都能与其穿透事件 100% 对账，包括负向事件和待补齐维度金额。
15. 作为订单台账用户，我希望按订单编号、客户姓名、客户单位或业务员搜索订单。
16. 作为订单台账用户，我希望按月份、订单状态、业务员、部门、小组、标准业务区域和客户单位组合筛选。
17. 作为数据查询用户，我希望所有表格和可增长业务清单都分页展示，避免一次铺开大量记录。
18. 作为数据查询用户，我希望默认每页显示 10 条，可选 10／20／50／100 条，并能直接点击页码或上一页／下一页。
19. 作为订单、账号、审计和分析穿透用户，我希望服务端分页与筛选状态保存在 URL 中，刷新或前进后退后仍可恢复。
20. 作为订单台账用户，我希望打开订单详情后返回列表时保留原筛选和当前位置。
21. 作为订单台账用户，我希望空数据、没有匹配结果、加载失败和权限不足呈现不同说明。
22. 作为有导出权限的用户，我希望导出所有符合当前条件且在权限范围内的数据，而不是只导出当前页。
23. 作为有导出权限的用户，我希望导出包含实际使用的筛选条件、导出时间和业务时区说明。
24. 作为审计人员，我希望每次条件导出记录操作者、时间、筛选范围、结果和请求标识。
25. 作为系统管理员，我希望业务导出权限不会因系统管理身份自动获得。
26. 作为产品负责人，我希望 2,850 笔基线数据的列表与导出不存在逐行查询，并留下可重复的查询预算证据。
27. 作为管理层用户，我希望查看各省份业绩贡献排名和中国地图，以便识别地区分布。
28. 作为管理层用户，我希望“外贸”作为 `EXT-TRADE` 单独展示，不被错误放入任何省份。
29. 作为管理层用户，我希望点击省份后查看该省份的客户单位排行。
30. 作为管理层用户，我希望点击客户单位后查看该单位按月份的业绩趋势。
31. 作为管理层用户，我希望从客户单位和月份继续下钻到订单及不可变事件。
32. 作为管理层用户，我希望地区和客户单位汇总按事件发生时保存的维度计算，订单后来变化不能改写历史。
33. 作为管理层用户，我希望同一订单的不同时期事件可以正确落入不同地区或客户单位。
34. 作为管理层用户，我希望缺少可信维度证据的历史金额进入“待补齐”项，并与已映射项合计后等于总账。
35. 作为数据责任人，我希望历史维度补齐只能使用受控来源证据、预检和显式确认，不能自动猜测。
36. 作为开发验收人员，我希望省份、客户单位和穿透测试使用脱敏合成数据，不把真实客户或订单提交到仓库。
37. 作为系统管理员，我希望搜索和分页查看账号，并查看账号当前固定角色组合。
38. 作为系统管理员，我希望受控修改既有账号的固定角色组合，并看到变更前后值。
39. 作为系统管理员，我希望创建、启停和重置账号密码，且临时密码只显示一次。
40. 作为系统管理员，我希望关闭人员任职或执行组织异动时遵守生效日期、唯一归属和负责人连续性规则。
41. 作为系统管理员，我希望账号、角色和组织变更全部进入不可修改的管理审计。
42. 作为目标审批人，我希望审批中心只显示当前账号有权处理的待办节点。
43. 作为目标审批人，我希望比较目标新旧版本、查看确认人和历史意见后再批准或拒绝。
44. 作为目标责任人，我希望在已认证会话中点击“确认目标”，不需要手写签名。
45. 作为目标责任人，我希望目标金额变化后重新确认具体版本，旧确认不能自动覆盖新版本。
46. 作为审计查询用户，我希望按人员、动作、实体和时间筛选审计记录。
47. 作为系统管理员，我希望只能查看账号、权限、组织和安全审计，系统管理身份不能查看全部业务审计。
48. 作为人事部或总经理，我希望只读查看全公司业务审计。
49. 作为其他业务角色，我希望只能查看与自身业务数据权限范围相关的审计记录。
50. 作为任意审计查看者，我希望密码、临时密码、会话令牌和其他秘密值永不出现在审计页面或导出中。
51. 作为任意用户，我希望每个主要页面有稳定 URL、页面标题和刷新恢复能力。
52. 作为任意用户，我希望无权限页面明确返回权限说明，不把无权限伪装为空数据。
53. 作为键盘用户，我希望导航、筛选、表格操作和对话框无需鼠标即可完成。
54. 作为键盘用户，我希望对话框进入时获得焦点，Tab 不离开对话框，Escape 可关闭，关闭后焦点返回触发按钮。
55. 作为使用辅助技术的用户，我希望按钮、输入框、状态和图表拥有可访问名称及文本等价信息。
56. 作为桌面用户，我希望在常见 1024px 及以上视口完成所有核心流程，不丢失退出或关键操作入口。
57. 作为任意用户，我希望加载、成功、失败、无结果和冲突都有持久、可恢复的反馈。
58. 作为维护者，我希望前端按业务页面拆分，后端保持领域规则集中，但不为了目录整齐改变现有行为。
59. 作为部署人员，我希望迁移账号、应用账号和备份账号采用最小权限，应用账号不能迁移结构或管理数据库角色。
60. 作为部署人员，我希望生产容器以非 root 用户运行，并具有明确健康检查、资源限制和日志轮转。
61. 作为安全负责人，我希望 Web 响应包含适用的安全头，可信代理、Origin 和 HTTPS 终止边界有明确契约。
62. 作为运维人员，我希望 API 输出结构化日志和请求 ID，以便关联登录、审批、导入和数据库故障。
63. 作为运维人员，我希望核心指标覆盖登录失败、审批失败、导入失败、请求错误和数据库不可用，并具有无高基数标签的告警条件。
64. 作为运维人员，我希望通过显式命令创建 PostgreSQL 备份、校验文件并恢复到另一个数据库，绝不覆盖来源库。
65. 作为运维人员，我希望恢复后自动核对 schema 版本、关键数据数量、健康状态和登录入口。
66. 作为部署人员，我希望在干净环境构建镜像、显式迁移空库、启动 Compose 并执行核心 smoke。
67. 作为部署人员，我希望有可执行的首次部署、升级、回退、备份、恢复、秘密轮换和故障排查手册。
68. 作为公司服务器管理员，我希望在服务器就绪后补充域名、HTTPS、访问范围、存储、RPO/RTO、监控平台和责任人，再执行实际验收。
69. 作为产品负责人，我希望公司服务器、真实数据、业务 UAT、部署和发布在分别授权前不会被工程命令自动执行。
70. 作为维护者，我希望每个 P1 切片都能独立演示、独立验证并保持主线门禁可通过。

## Implementation Decisions

- P1 仍覆盖 #10—#15。当前产品只覆盖桌面 Web 和仓库内生产准备；移动端 #57 已取消，不再是 #14 或 P1 的完成门禁。公司服务器验收仍是 #15 的后续人工门禁。
- 继续使用模块化单体、React、Fastify 和 PostgreSQL，不引入微服务、消息队列、GraphQL 或第二套数据库。
- 看板默认使用 `Asia/Shanghai` 当前自然月，并允许选择历史年份和月份；不能再以“最新存在事件的月份”代替当前业务月。
- 当前月时间进度采用“截至当天的自然日序号 ÷ 当月自然日总数”，完整历史月固定为 100%，未来月不计算；时间进度偏差为达成率减时间进度。目标未生效或目标金额不大于零时也不计算，只显示稳定原因码。
- 个人、小组、部门和销售范围使用各自层级的生效目标与事件范围。个人业绩不包含下属业绩；团队汇总使用事件发生时组织归属快照。
- 看板、正式报表和导出共享同一服务端汇总语义；前端不自行重算正式金额或绕过目标生效门禁。
- 指标穿透返回构成该指标的订单和不可变事件，并携带足够信息解释正向、负向、状态变化、组织归属和分析维度。
- 订单、账号、审计、分析穿透和记账治理清单使用服务端页码分页并返回精确 `totalCount`；其他已完整加载的数据表格与可增长业务清单在客户端分页。统一默认 10 条，可选 10／20／50／100 条，展示总条数、总页数、当前页、上一页／下一页和可点击页码。订单、审计和分析穿透由首次页码查询返回绑定用户、筛选与 cutoff 的不透明快照并写入 URL；后续翻页复用，筛选、每页条数或主动刷新时重建。超出有效页范围时回到可用页。既有游标 API 保持向后兼容，但桌面 Web 不再以游标作为分页交互。
- 自由搜索覆盖订单编号、客户姓名、客户单位和业务员；结构化筛选覆盖月份、订单状态、业务员、部门、小组、标准业务区域和客户单位。
- 列表与导出共享一个服务端查询合同、权限谓词和筛选解释。订单台账导出为带 UTF-8 BOM 的 CSV，每个匹配订单一行，固定包含订单编号、客户、客户单位、业务员、部门、小组、来源区域原文、标准业务区域、到样日期、当前营业额、当前计入金额和状态；用户来源文本防止 CSV 公式注入。导出覆盖全部匹配结果而不是当前页，并采用流式或分批读取，不能形成逐行查询。导出审计只保存筛选摘要、行数、结果状态、请求 ID 和完成文件的 SHA-256，不保存导出正文。
- 页面 URL 保存页面、筛选、排序和分页状态。优先复用浏览器 History API；只有出现其无法清晰承载的嵌套路由需求时才评估路由依赖。
- 每笔事件必须具有唯一、不可修改的业绩分析维度快照，保存事件发生时的标准业务区域、来源区域原文和客户单位。新事件在同一业务事务内写入快照；物理上使用事件列还是一对一关联表，由实现前结合既有不可变约束选择最小方案。
- 已存在但缺少分析维度的历史事件不连接订单当前投影。分析结果必须单列待补齐事件数量和金额，使“已映射维度 + 待补齐”与事件总账对账。
- 历史维度补齐采用受控来源证据、预检、显式确认、幂等和审计；本规格只实现能力和合成数据验收，不执行真实工作簿补齐。
- 省份视图使用仓库内静态中国省级地理资源，不依赖运行时外部地图服务。`EXT-TRADE` 独立展示，客户单位仍是来源文本，不在 P1 引入客户主数据系统。
- 系统管理员可以受控修改账号的固定角色组合，但不能创建自定义权限。账号、角色、组织和安全操作进入管理审计。
- 审计查询按 ADR-0029 分域授权；服务端在读取时同时执行角色能力、业务数据范围和字段脱敏，前端隐藏不构成授权。订单、业绩事件、导出和导入审计按事件发生时组织归属快照授权；目标和审批审计按目标版本保存的责任人／组织范围授权；账号、角色、组织和安全审计只进入系统管理域。历史审计不得用当前组织关系追溯扩权。
- 目标确认按 ADR-0030 使用已认证会话中的显式确认动作。保存稳定人员身份、账号、目标版本、确认声明、确认时间和不可修改审计，不采集手写签名图片。
- 审批中心聚合当前用户可处理的节点，并提供版本比较、意见和历史；不改变既有目标状态机、职责分离或人事最终审批规则。
- 前端只在新增或修改页面时提取路由页与共享控件，优先复用现有设计令牌，不以目录数量、文件行数或全面重写作为验收条件；依赖方向不能把领域规则移入页面。
- 当前产品以 1024px 及以上桌面视口为响应目标，保持语义表格和横向滚动。当前没有 390×844 移动端支持承诺；若未来新增移动产品，必须重新建立独立范围和验收矩阵。
- 无障碍目标采用现有 UX 合同中的 WCAG 2.2 AA 目标。自动扫描只声明核心流程中 WCAG 2.2 A/AA 的 critical/serious 已知违规为零；键盘、焦点、图表文本等另行验证，不把自动扫描宣称为全站合规证明。必要时只增加与 Playwright 集成的最小自动扫描依赖，不新增第二套浏览器测试框架。
- 生产数据库拆分迁移、应用和备份职责；所有一次性作业仍显式执行，API 启动不自动迁移、初始化、备份、恢复或导入。
- 生产容器使用非 root 用户。隔离默认资源上限为 API 1 CPU/512 MiB、Web 0.5 CPU/128 MiB、PostgreSQL 2 CPU/1 GiB，实际服务器验收时再校准；Compose 使用健康检查、重启策略及每服务 `10m × 5` 的日志轮转。秘密只通过部署环境注入，不写入镜像或日志。
- API liveness 只证明进程可响应，readiness 同时证明数据库可连接且 schema 版本正确；Web 提供独立静态健康入口。Web 至少设置 `Content-Security-Policy`（同源脚本／样式／连接、禁止对象和框架嵌入）、`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、禁用摄像头／麦克风／定位的 `Permissions-Policy` 和 `Cross-Origin-Opener-Policy: same-origin`；HSTS 由实际 HTTPS 终止层验收。
- 结构化 stdout 至少包含时间、级别、服务、请求 ID、方法、路由模板、状态码、耗时、操作类别、结果和稳定原因码，不包含密码、令牌或业务明细。内部指标至少覆盖 HTTP 请求量／错误／耗时、登录失败、审批失败、导入失败和数据库就绪；标签只允许路由模板、方法、状态类别、操作、结果和原因码，禁止账号、人员、订单或客户等高基数值。告警采集与通知复用公司现有平台，不在仓库内建设监控平台。
- 备份使用 PostgreSQL 自定义格式并生成 SHA-256 清单。工具只创建、校验和恢复到显式指定的新目标；恢复命令必须拒绝来源库与目标库相同。恢复验收核对 schema 版本、关键表数量与稳定摘要、readiness 和登录 smoke，并证明来源库前后摘要不变。
- CI 与本地门禁增加生产镜像构建和隔离 Compose smoke；公司服务器实际部署、HTTPS、备份存储和告警联通仍需外部环境与授权。
- 不修改任何已应用迁移；所有 schema 变化使用新的只追加迁移，并验证空库、既有库升级和失败回滚。

## Testing Decisions

- 测试只验证外部可观察行为和业务不变量，不锁定私有函数、SQL 文本、组件目录或视觉实现细节。
- 第一验收入口是 API 与隔离 PostgreSQL 集成测试，覆盖权限范围、目标门禁、四层汇总、差距与达成率、稳定分页、组合筛选、条件导出、分析维度快照、待补齐对账、账号角色修改、审批待办和审计可见范围。
- API 测试沿用现有真实 PostgreSQL、应用装配和角色化测试夹具；不使用 SQLite、内存数据库或伪造数据访问层。
- 数据库迁移测试覆盖空库升级、既有库升级、不可变约束、分析维度唯一性、角色最小权限和失败不留半成品。
- 查询性能同时使用小基线和 2,850 笔／4,701 事件等价合成基线。规模增长时，列表数据库读取不超过 2 次、指标穿透不超过 3 次、单个分析请求不超过 4 次、导出不超过 2 次，且两种规模的读取次数差不超过 1。关键查询保存 EXPLAIN JSON，并阻断逐输出行执行的 SubPlan 或等价逐行查询；时间阈值只作为同一环境的回归信号。
- 第二验收入口是桌面 Chromium Playwright E2E，覆盖各角色看板、URL 恢复、筛选分页、条件导出、分析穿透、账号／组织管理、目标确认、审批中心和审计查询。
- 浏览器测试使用真实 API 与隔离 PostgreSQL，不引入 Cypress、第二套浏览器驱动或伪造 API。
- Playwright 复用一个最小全栈 fixture，统一创建隔离数据库、迁移、种子、API 端口、日志和定向清理；测试仍保持相互隔离，失败时保留最短诊断证据。
- 浏览器验收覆盖 1280px 全部 P1 核心流程，并为 #10—#13 每项至少选择一条核心流程在 1024px 运行；使用 `zh-CN` 和 `Asia/Shanghai`。六个核心页面的自动扫描要求 WCAG 2.2 A/AA critical/serious 已知违规为零，键盘导航、焦点管理、图表文本等另有明确断言。
- 第三验收入口是隔离 Docker Compose：干净构建镜像、显式迁移空库、健康／就绪检查、应用最小权限、Web 安全头、结构化日志、备份、恢复到新库和核心 smoke。
- 单一 Compose 验收命令使用独立项目名、端口和卷，依次执行 build、migrate、up、ready、smoke、backup、restore-new-db、校验；无论成功或失败都只清理本次明确创建的资源。
- Compose 验收使用独立项目名、未占用端口和独立卷；执行前核对同机容器与端口，结束后只清理本次创建的隔离资源。
- 备份恢复测试必须证明来源库未改变、目标库 schema 和关键计数一致、恢复后服务可就绪；不使用真实业务库或真实工作簿。
- 迁移执行保留 CLI 默认入口，同时提供可由测试传入临时迁移集合的最小 seam；故意失败的迁移必须证明该迁移的 schema 记录、对象和数据均未留下半成品。
- 每个实现切片先留下一个会失败的最高层回归，再做最小实现；切片结束运行相关回归，全阶段结束运行项目完整门禁和双轴代码审查。

## Out of Scope

- 当前产品不提供移动端布局或触屏核心流程；#57 已取消并永久移出当前 P1。未来若新增移动产品，必须建立新的明确范围和验收 Issue。
- 当前无公司服务器，不执行实际域名、证书、HTTPS、内网／VPN、防火墙、正式秘密、备份存储、告警通知、负载、故障或生产回退验收；这些仍是本规格最终范围内的后续 #15 Gate。
- 不执行真实组织映射、真实 Excel 维度补齐、正式历史迁移、业务 UAT、生产部署、Tag、Release 或版本发布。
- 不采集手写签名图片，不接入 CA 或第三方电子签名平台。
- 不接入运行时外部地图服务，不建设客户主数据系统。
- 不包含 P2 的轻流 API 同步、2024—2025 历史明细或 CI 深度加固。
- 不引入微服务、消息队列、GraphQL、第二套数据库、第二套浏览器测试框架、Storybook 或独立 Mock API 体系。
- 不修改或删除真实 Excel、旧来源证据、现有开发数据库或同机其他项目资源。
