## 1. 范围与完成定义

本计划只覆盖 GitHub P0 #1—#9，以及产品负责人明确补充的“除人工录入外，支持未来多种线下 Excel 受控导入”。不包含 P1 页面打磨、轻流 API、生产部署、真实数据执行、发布或仓库设置变更。

P0 完成必须同时满足：

1. #1—#9 的适用验收条件均有自动化证据；
2. 人工录入、历史导入和 Excel 导入共用同一套服务端领域规则；
3. 全新临时数据库可迁移、测试和清理，既有数据库可按新增迁移升级；
4. API、浏览器、数据库约束三层证据与风险相称；
5. 未经授权，不导入真实文件、不执行生产作业、不修改 GitHub Issue、分支保护或仓库设置。

## 2. 已验证的当前事实

- API 只有 `performance.test.ts` 中 4 个领域单元测试；Web 使用 `node --test`，当前没有 Web 测试文件，也没有 Playwright 或 CI 工作流。
- `server.ts` 在模块顶层创建并监听 Fastify，尚无可供隔离测试复用的应用工厂。
- 组织任职直接绑定 `users`，成员归属、组长职责和主管职责混在 `org_assignments`；数据库只校验日期先后，没有任职重叠和跨部门约束。
- 业绩 API 接收客户端填写的业务日期与组织名称；列表、看板、组织和导出没有统一的数据范围策略。
- `performance_events` 已有 UPDATE/DELETE 拒绝触发器，但没有记账期间实体、重开授权或请求幂等键。
- 目标修改申请只有创建入口，`goal_linkage_decisions` 尚无代码入口。
- 密码规则当前分别为 8 位、12 位和生产 12 位；首次改密没有服务端全局门禁。
- 生产 Dockerfile 复制本地 Excel，并在容器启动命令中串联迁移、seed、历史导入和 API。
- `start_all.bat` 的开发启动链会自动执行历史导入。
- `CLAUDE.md` 不存在；行为规则来自根目录 `AGENTS.md`。

## 3. 权威冲突与处理

### 3.1 Issue #8 密码验收文字已过时

Issue #8 仍写有“8 位临时密码被拒绝”，与产品负责人后来确认的规则冲突。实现与本地验收以最新确认规则为准：密码 6—128 位，必须包含英文字母、数字和符号，并显示强度提示。长度少于 6 位或缺少任一字符类别时拒绝；满足组合规则的 8 位密码不能仅因长度为 8 被拒绝。

修改 GitHub Issue 正文属于远程写入，需要另行授权；本阶段不修改。

### 3.2 旧规格和启动说明需要随实现同步

`docs/v1-scope.md`、`docs/development.md` 和 `start_all.bat` 仍描述“仅人工逐条录入”或启动时自动导入历史 Excel。它们不得覆盖 ADR-0022、ADR-0027 和本计划；对应文档在 #9/Excel 切片中与代码一起更新。

## 5. 推荐实施顺序与任务

### S1 — #1A：建立隔离验证骨架

产物：

- 从 `server.ts` 提取不监听端口的 Fastify 应用工厂，生产入口只负责监听和关闭。
- 建立临时 PostgreSQL 数据库创建、迁移、fixture、失败清理和防误连保护。
- 增加 API 集成测试入口、Web 组件/浏览器测试入口和 Playwright 基础配置。
- 建立本地 CI 等价命令；现有已通过行为先纳入必过门禁。
- 审计发现的失败场景按 Issue 保存为回归规格；每个业务切片先证明红灯，再修到绿灯。

验证：临时库名称随机且受保护；故意失败后仍被清理；重复运行不污染开发库；API/Web 至少各有一个真实测试被执行。

主要触点：`apps/api/src/server.ts`、新增测试支持模块、各 workspace `package.json`、`.github/workflows/`。

人工门禁：启用 `main` 分支保护属于 GitHub 远程设置，必须在本地 CI 证据通过后单独授权。

### S2 — #8：统一认证安全基线

产物：

- 单一服务端密码校验器和随机临时密码生成器，覆盖创建、重置、改密和 bootstrap。
- 6—128 位、字母+数字+符号规则；Web 实时显示弱/中/强，不向外部发送密码。
- 首次改密服务端全局门禁，仅放行 `me`、`logout`、`change-password` 和必要 CSRF 入口。
- 账号/IP 登录限速、`last_seen_at` 更新、闲置/绝对过期、会话清理与撤销。
- 登录、改密、重置、停用、失败与限速审计；补齐 Origin/CSRF 防护。
- 账号管理页面使用系统生成临时密码，不接受管理员自选重置密码。

验证：认证 API 集成测试、旧会话撤销测试、直接 API 绕过测试、浏览器首次改密 E2E、日志敏感信息检查。

主要触点：`security/password.ts`、`security/session.ts`、`modules/auth.ts`、`modules/admin.ts`、会话相关新增迁移、账号 UI。

### S3 — #9A：恢复空系统构建并拆分一次性作业

产物：

- API 镜像不复制 Excel，运行命令只启动 API；结构落后时启动/就绪检查明确失败。
- 保留显式 `db:migrate`，拆出 `admin:bootstrap` 与仅开发可用的 `dev:seed`。
- 一次性作业使用数据库锁，重复执行幂等跳过或安全拒绝。
- `start_all.bat` 可显式编排开发迁移和演示 seed，但默认不再导入历史业务文件。
- 更新开发、部署和范围说明，消除“启动即灌数”的旧描述。

验证：不含任何 Excel 的干净构建上下文可以构建 API/Web；空库迁移后启动；重复作业与并发作业测试；镜像内容检查不含业务文件。

主要触点：API Dockerfile、Compose、CLI、`scripts/dev-start.mjs`、根脚本和部署文档。

人工门禁：这里只验证本地干净环境，不执行公司服务器部署或正式管理员初始化。

### S4 — #3：建立稳定人员身份、有效组织和服务端快照

产物：

- 使用新增迁移建立稳定人员身份，并把登录账号作为可选绑定；不修改已应用的 001—006 迁移。
- 分离人员小组归属与组长/主管管理职责，支持有效期和同一负责人兼管多个范围。
- 数据库与服务端共同拒绝重叠成员归属、跨部门小组、不存在负责人和无人/多人负责期间。
- 建立 `OrgResolver`：按人员和事件发生时间解析唯一成员归属、组长与主管。
- 业绩写入不再接收客户端权威组织名称，事件固化稳定标识和展示快照。
- 建立 59 人、16 组、5 部门和额外 4 人的映射预检与差异报告。

验证：迁移升级/重放测试、任职边界和重叠测试、A 组 +100/B 组 -100 示例、找不到唯一任职时整笔阻断。

主要触点：新增迁移、`modules/admin.ts`、新增组织领域模块、`modules/performance.ts`、组织管理 UI。

人工门禁：真实负责人及生效日期、额外 4 人任职日期必须由人事确认；缺失时只能验证预检失败，不能伪造正式映射。

### S5 — #2：统一角色权限与数据范围

产物：

- 一个服务端 `AuthorizationPolicy` 定义角色能力及 self/group/department/all/none 范围。
- 所有订单、事件、看板、目标、组织、导出和审批待办共用范围谓词；详情与导出不得绕过列表范围。
- 账号管理提供只读角色权限矩阵，内容从同一服务端定义生成。
- 正式业绩报表按本层级目标生效状态门禁，原始账本读取与正式报表明确分开。

验证：每个角色对每类资源都有正向和越权集成测试；多角色按已确认规则合并；无业务角色的系统管理员得到 403；浏览器按钮与直接 API 结果一致。

主要触点：新增授权模块、全部 API route、查询 SQL、账号管理与报表 UI。

### S6 — #5：建立记账期间与受控重开

产物：

- 新增记账期间、关闭版本、重开申请/授权及审计数据结构。
- 服务器确定操作时间和记账月；普通接口不能伪造操作月或回填关闭期间。
- 销售助理组长申请、人事审批、销售助理组长在获批订单/类型内一次性追加，人事不能代为改业绩。
- 事件命令使用幂等键和订单行锁；显示顺序、投影重放和报表顺序统一。

验证：跨月暂停/重启、关闭/拒绝/获批范围、24 小时或完成后失效、重复/并发提交、重新关账版本差异测试。

主要触点：新增迁移、记账期间领域模块、`modules/performance.ts`、管理与审批 UI。

### S7 — #4：闭合历史与新订单事件链

产物：

- `PerformanceLedger` 统一人工录入和后续事件命令，组合使用 `OrgResolver`、记账期间与授权策略。
- 订单详情返回完整不可变事件链；P0 仅增加按精确订单编号定位，不扩展到 #11 的通用分页筛选。
- UI 不再要求用户填写组长/主管；只显示服务端解析结果和当前状态允许的操作。
- `legacy_adjustment` 原样展示；净额为正/单零行按已确认规则投影，多行净零或负数进入待核并锁定操作。

验证：历史 active/zero/待核各一条正反路径；`[110,-10,-100,+100]` 重放；UI/API 非法状态一致拒绝；数据库 UPDATE/DELETE 触发器回归测试。

主要触点：业绩领域模块、`modules/performance.ts`、订单页和事件详情 UI。

### S8 — Excel 补充需求 + #9B：可复用受控导入

产物：

- 标准业绩模板，以及版本化导入配置、导入批次、行级结果和来源证据模型。
- 销售助理/组长上传并预检，只有组长确认；人事审批配置，不逐批审批业绩数据。
- 仅接受未加密 `.xlsx` 固定值；未知表头、公式、宏、外部连接和模糊列映射阻断。
- 每批先完整解析和预演，任一阻断错误则全批不写入；确认原子提交或整批回滚。
- 稳定来源记录标识保证幂等；获批历史格式才允许使用文件 SHA-256 + 工作表 + 来源行号，并检测跨文件疑似重复。
- 业务区域同时保存来源原文和标准映射版本；“外贸”保留为独立区域；历史行固定为 `legacy_adjustment`，不猜暂停/重启语义。
- 显式历史导入保留 4,701 事件、2,850 订单和 14,675,659.07 元的对账证据。

验证：标准模板和至少两个不同列布局的配置测试；预检零写入；单行错误整批回滚；重复文件/重复来源记录；跨文件疑似重复；权限越权；历史总量/总额/哈希对账。

主要触点：新增导入迁移与 `ImportJob`、上传/预检/确认 API、导入 UI、标准模板、历史 CLI。

人工门禁：31 种来源业务区域映射已确认“外贸”独立使用 `EXT-TRADE`，其余精确映射仍须由业务负责人确认；真实 Excel 上传、历史正式导入和证据文件删除均需单独授权。

### S9 — #6：目标创建、层级与职责分离

产物：

- `GoalWorkflow` 统一校验月份、层级、父目标、责任人资格、直属关系和操作人权限。
- 顶层销售经理目标允许无父级；其他层级必须连接同月合法直属父目标。
- 下达人、责任人签名者、总经理和人事审批人按已确认人员身份执行职责分离。
- UI 使用按组织范围返回的选择器，不手填账号或数据库 ID；数据库错误转换为稳定 4xx 业务错误。

验证：四层目标正向路径；非法父层级、跨月、错误责任人、自签自批、多角色绕过；销售经理→总经理→人事 E2E。

主要触点：目标迁移约束、`modules/goals.ts`、新增目标领域模块、目标 UI。

人工门禁：销售经理总目标在总经理第一道审批前是否允许下发下级草稿，仍需产品负责人确认。

### S10 — #7：目标修改、联动、重签与审计闭环

产物：

- 修改申请列表、待办、接受、拒绝、撤回、创建唯一新版本、责任人重签和人事最终审批。
- 同一目标只允许一条有效待处理申请；重复提交幂等，并发操作只有首个合法操作成功。
- 下级目标变化后强制 `keep_parent` 或 `adjust_parent`；前者保留本级签名，后者逐级创建申请而不自动改金额。
- 页面展示版本差异、分配差额、审批意见与完整操作历史。
- 每个签名、选择、审批、拒绝和版本替代写入审计。

验证：业务员→组长、组长→主管、主管→销售经理三条链；拒绝/撤回/重提；并发和重复审批；未分配/超分配；两种联动选择 E2E。

主要触点：目标迁移约束、`modules/goals.ts`、目标领域模块、审批中心 UI。

### S11 — #1B：收口完整门禁

产物：

- 将全部 P0 回归场景纳入必过集成测试和浏览器 E2E，不再保留允许失败的已知 P0 场景。
- CI 必过：typecheck、unit、integration、Web tests、E2E、build、`npm audit --omit=dev`、Compose 配置和干净迁移。
- 形成逐 Issue 的命令、结果、数据库隔离证明和浏览器流程证据。

验证：全新检出在隔离环境重复运行两次结果一致；失败能使 CI 非零退出；开发数据库计数和哈希在测试前后不变。

人工门禁：是否启用分支保护、是否写回 Issue/评论或关闭 Issue，必须逐项获得 GitHub 写入授权。

## 6. 每个切片的统一执行规则

每个切片都按以下顺序实施，不能用最终绿灯替代红灯证据：

1. 固定该切片涉及的 Issue 验收条目和已确认 ADR；
2. 添加最小失败测试并记录失败原因；
3. 实施最小代码和新增迁移，不修改已应用迁移；
4. 运行该切片的定向测试，再运行全量 typecheck、测试和 build；
5. 涉及数据库时验证空库迁移、既有库升级、重复执行和失败回滚；
6. 涉及 UI 时运行真实浏览器正向、拒绝和直接 API 绕过路径；
7. 展示差异、验证证据和未决问题，等待用户确认后再进入下一切片。

## 7. 推荐 Skill 顺序

当前阶段只产出任务拆分，不自动进入下列 Skill。用户确认开始某个实施切片后，推荐流程为：

1. `codebase-design`：仅在 #3、#2、#5、#6 和 Excel/#9B 开始前冻结模块接口与数据所有权；产物是最小接口草图和迁移边界。
2. `tdd`：每个切片先建立可复现红灯，再实施到绿灯；产物是定向测试、修复代码和命令证据。
3. `diagnosing-bugs`：只在红灯原因不明、重复失败或性能异常时进入；产物是根因和最小复现，不自动扩大为修复。
4. `code-review`：每个切片实现和验证完成后审查固定差异；产物是按优先级列出的发现或无阻塞结论。

涉及业务范围、数据含义、权限、生产数据、GitHub 写入、发布或不可逆操作时，即使 Skill 建议继续，也必须停下等待人工确认。

## 8. 当前仍由用户或责任人控制的决策

1. 销售经理总目标第一道审批前是否允许下发下级草稿；
